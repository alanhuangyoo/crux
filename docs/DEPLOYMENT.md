# 4 张 H20 上跑 Terminal-Bench:方案

> 数据来自 h20-44 卡 0/2/6/7 的实测,每个配置独占四张卡串行测量。
> 待补:Flash-Next 的八组配置(下载中)。

## Agent:crux-terminus

十任务切片,同模型同部署下的横向对比:

| harness | 解出 |
|---|---|
| crux-terminus | 7/10 |
| terminus-2(官方脚手架) | 7/10 |
| crux(mini-swe-agent 基座) | 6/10 |
| codex + Qwen3.8-27B | 5/9 |
| codex + GPT-5.6-sol | 4/9 |

crux-terminus 继承 Terminus,只改三处:

1. **全或无计分提示词** —— 要求逐条举证而非凭记忆
2. **`crux submit`** —— 提交前重跑所有绑定检查,不通过就拒绝
3. **截断重试关思考** —— 见下

第三条是修上游的一个逻辑错误。Terminus 遇到输出截断时,发一条"你超长了,请分块重发"然后**用同样条件重试**。这条建议假设模型是在写命令时超长,但实测它是在**思维链里**超长 —— 连 `<response>` 都没开始写,分块无从谈起,重试只会复现螺旋。一个任务因此第一次烧 17 分钟、重试烧 29 分钟,共执行零条命令。

改成重试时关掉思考后:

| | 原版 | crux-terminus |
|---|---|---|
| 最长单步 | 715s | **112s** |
| 每步 token 中位 | 3,315 | **1,266** |
| 十任务耗时 | 33m17s | **21m7s** |

分数持平但快 37%。

## 投机解码:关闭

稠密 27B 上测了五种配置,全部为负:

| 配置 | conc1 | conc8 | conc16 | 接受长度 |
|---|---|---|---|---|
| **无投机** | **141.4** | **129.7** | **122.5** | — |
| MTP 默认 | 108.8 | 85.5 | 77.7 | 3.89 / 4 |
| MTP + 图上限 | 109.2 | 94.4 | 80.6 | 3.91 |
| MTP 单步 | 116.4 | 107.6 | 98.4 | **2.00 / 2** |
| MTP decode 模式 | 109.2 | 94.5 | 80.6 | 3.91 |
| DSpark(社区推荐) | 101.4 | 73.2 | 46.5 | 0.15-0.26 |

最有说服力的是「MTP 单步」那行:草稿 **100% 全中**,仍比不投机慢。

草稿全部命中依然更慢,说明成本不在猜错,在**验证本身**。这个模型 64 层里 48 层是线性注意力,verify 要为每个草稿 token 回滚并重放 SSM 状态 —— 开销与模型层数成正比,与「draft 只有一层」无关。所以接受率再高也救不回来。

社区 recipe 推荐投机解码,是在 H200 / RTX PRO 6000 上测的。**同样的参数,在 H20 上结论相反**:H20 是 H100 级带宽配约 15% 的算力,实测负载下 SM 100% 而显存带宽仅 27-32%,没有闲置算力可供投机。

## 并行方式与引擎(稠密 27B,四张卡实测)

| 配置 | conc1 | conc8 | conc16 | KV 容量 |
|---|---|---|---|---|
| **SGLang TP4 + BF16 KV** | **144.8** | **133.4** | **125.5** | 370 万 |
| SGLang TP4 + FP8 KV | 141.6 | 129.7 | 122.3 | 739 万 |
| vLLM TP4 + FP8 KV | 129.1 | 125.6 | 119.4 | **1489 万** |
| SGLang TP2 + DP2 | 95.1 | 91.1 | 88.3 | 348 万 |
| SGLang TP4 + torch.compile | OOM(inductor 编译期显存被 KV 池占满) | | | |
| vLLM TP4 + BF16 KV | 失败(transformers 与 Qwen3VL 视频处理器不兼容) | | | |

**TP 越高越好。** `TP2+DP2` 掉 34% 是最直接的证据:把四张卡拆成两组各跑一份,
单流可用算力减半 —— 而算力正是这台机器稀缺的那一项。同理 TP2→TP4 当初也是翻倍
(65 → 144 tok/s)。任何「分组」策略在这里都是负收益。

**FP8 KV 不是免费的**:同机同时段对照下它比 BF16 慢约 2.5%,换来的是两倍 KV 容量。
所以两个场景分开选:

- **跑 bench** → BF16 KV。评测按单任务墙钟计时,单流延迟就是一切,370 万 token
  足够 16 并发(实测 P99 上下文 113K)。
- **对外服务** → FP8 KV。多人共用时能挂多少长会话比 2.5% 更要紧。

vLLM 慢 5-12% 但 KV 池是 SGLang 的两倍,是「极多用户、可容忍稍慢」场景的备选。

## 待补

Flash-Next(176B 总参数 / 6B 激活,GDN + QSA 混合 MoE)。它与稠密模型的取舍方向
相反 —— 省算力、费显存 —— 正好对上这张卡的强弱项,所以上面关于投机解码的结论
未必适用,需要重测而非套用。

### 权重完整性

第一次拉下来的 131 个分片里有 39 个是短的 —— 有几个近乎空文件 —— 而文件**个数**
是齐的,所以「数分片」这个检查看着通过了。safetensors 报 `incomplete metadata`,
在那之前的 `output_size 160 不能被 block_n 128 整除` 多半也是同一批残缺文件被读成
了错误的形状。

三次都栽在同一件事上:**检查「还活着」而不是「在前进」**。

| 现象 | 失效的检查 |
|---|---|
| `hf download` 挂死半小时 | 只看 systemd 单元是否 active |
| `curl -C -` 假续传出 39 个残缺文件 | 只数分片个数 |
| 限速后连接停滞 | 监听间隔比停滞还长 |

最后可靠的做法是:逐个文件比对 manifest 里的字节数,串行下载,不匹配就删掉重来
(续传到损坏的前缀上正是问题的来源),并给 curl 加 `--speed-limit/--speed-time`
—— `--retry` 只对**失败**生效,对**挂着不动**的连接无效。

**发布版引擎都还不支持它**:SGLang 0.5.18 与 vLLM 0.28.0 均无 `Qwen4Exp` 实现
(vLLM 0.28 的 transformers 5.16 认得 config,但模型注册表里没有对应条目)。官方
cookbook 的基准数据标注 `sglang_version: "qwen4-main @ e17062a1d"`,即上游的
`qwen4-main` 分支而非任何 tag —— 该分支下有 `qwen4_exp.py` 与 `qwen4_exp_mtp.py`。
从源码安装该分支需要 Rust 工具链(它带 Rust 写的 router 扩展,缺 cargo 会在
`build_editable` 阶段失败)。
