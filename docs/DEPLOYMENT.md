# 4 张 H20 上跑 Terminal-Bench:方案

> 数据来自 h20-44 卡 0/2/6/7 的实测,每个配置独占四张卡串行测量。
> 待补:Flash-Next 的八组配置(下载中)。

## Agent:crux-terminus

十任务切片,同模型同部署下的横向对比:

| harness | 解出 |
|---|---|
| crux-terminus | 7/10 |
| terminus-2(官方脚手架) | 7/10 |
| crux(mini-swe-agent 基座) | 6/10 |
| codex + Qwen3.8-27B | 5/9 |
| codex + GPT-5.6-sol | 4/9 |

crux-terminus 继承 Terminus,只改三处:

1. **全或无计分提示词** —— 要求逐条举证而非凭记忆
2. **`crux submit`** —— 提交前重跑所有绑定检查,不通过就拒绝
3. **截断重试关思考** —— 见下

第三条是修上游的一个逻辑错误。Terminus 遇到输出截断时,发一条"你超长了,请分块重发"然后**用同样条件重试**。这条建议假设模型是在写命令时超长,但实测它是在**思维链里**超长 —— 连 `<response>` 都没开始写,分块无从谈起,重试只会复现螺旋。一个任务因此第一次烧 17 分钟、重试烧 29 分钟,共执行零条命令。

改成重试时关掉思考后:

| | 原版 | crux-terminus |
|---|---|---|
| 最长单步 | 715s | **112s** |
| 每步 token 中位 | 3,315 | **1,266** |
| 十任务耗时 | 33m17s | **21m7s** |

分数持平但快 37%。

## 投机解码:关闭

稠密 27B 上测了五种配置,全部为负:

| 配置 | conc1 | conc8 | conc16 | 接受长度 |
|---|---|---|---|---|
| **无投机** | **141.4** | **129.7** | **122.5** | — |
| MTP 默认 | 108.8 | 85.5 | 77.7 | 3.89 / 4 |
| MTP + 图上限 | 109.2 | 94.4 | 80.6 | 3.91 |
| MTP 单步 | 116.4 | 107.6 | 98.4 | **2.00 / 2** |
| MTP decode 模式 | 109.2 | 94.5 | 80.6 | 3.91 |
| DSpark(社区推荐) | 101.4 | 73.2 | 46.5 | 0.15-0.26 |

最有说服力的是「MTP 单步」那行:草稿 **100% 全中**,仍比不投机慢。

草稿全部命中依然更慢,说明成本不在猜错,在**验证本身**。这个模型 64 层里 48 层是线性注意力,verify 要为每个草稿 token 回滚并重放 SSM 状态 —— 开销与模型层数成正比,与「draft 只有一层」无关。所以接受率再高也救不回来。

社区 recipe 推荐投机解码,是在 H200 / RTX PRO 6000 上测的。**同样的参数,在 H20 上结论相反**:H20 是 H100 级带宽配约 15% 的算力,实测负载下 SM 100% 而显存带宽仅 27-32%,没有闲置算力可供投机。

## 待补

Flash-Next(MoE,512 专家激活 10)的八组配置。它与稠密模型的取舍方向相反 ——
省算力、费显存 —— 正好对上这张卡的强弱项,所以上面关于投机解码的结论未必适用,
需要重测而非套用。
