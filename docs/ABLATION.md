# 消融实验设计

**尚未运行。** 本文定义要问的问题和判读标准，避免事后对着数字编故事。

## 前提

三条约束决定了实验怎么设计：

- **并发固定 24。** 任务带超时，并发变化会改变分数。混用不同并发的结果不可比。
- **每个变体只改一个开关。** 同时改两处，分数变化归因不了。
- **配置写进轨迹。** `AgentContext.metadata.config` 记录完整配置，事后可核对某一行到底跑的是什么。

## 变体

变体定义在 [`src/crux/config.py`](../src/crux/config.py) 的 `VARIANTS`，用
`--ak variant=<名字>` 选择。

| 变体 | 改动 | 要回答的问题 |
|---|---|---|
| `default` | — | 基线 |
| `no_compaction` | 关闭上下文压缩 | 压缩到底有没有用？ |
| `no_apply_patch` | 不注入 apply_patch | 结构化编辑值不值得注入工具？ |
| `steps_60` | 步数上限 150 → 60 | 提高步数上限到底有没有换来分数？ |
| `pane_60` | 终端高度 40 → 60 | 每轮多看 20 行，值不值那些 token？ |
| `bare` | 同时关掉压缩和 apply_patch | v2 架构本身值多少分（近似纯 Terminus 基线） |

## 判读

**`no_compaction`**：deepseek-v4-flash 的上下文窗口是 100 万 token，压缩几乎不会触发，
所以这个变体在该模型上**预期无差异**。真有差异反而说明压缩逻辑有副作用，要查。
它的价值要换到小窗口模型才体现——因此这一项应该跨模型跑，而不是只在 flash 上跑。

**`steps_60`**：默认值已从 60 提到 150——首次干净运行中 5 个任务全部在推进途中撞上限，
且 harbor 对 agent 超时是「记录并照常评分」而非判 error，所以低上限只是白白丢弃本会被计分的工作。
这个变体是那次提高的对照组：若 60 与 150 同分，说明预算从来不是瓶颈，多花的钱是浪费。

**`bare`**：它和 `default` 的差值，就是 apply_patch 加压缩这两项加起来的总价值。
如果差值接近零，说明 v2 的收益全部来自 tmux 架构本身，后续精力该投向别处。

## 规模

74 任务 × 5 trials = 370 trials/变体。6 个变体 = 2220 trials。

按冒烟实测的单任务成本推算，一个变体约 60 美元，全套约 360 美元。
**不要一次跑完**：先用 `default` 和 `bare` 两个变体确认差值确实存在，
再决定其余四个值不值得跑。

## 顺序

1. `default` 全量 —— 建立基准分数（也是提交用的那次）
2. `bare` 全量 —— 确认附加机制整体是否有效
3. 若 (2) 显示有效，再拆 `no_compaction` / `no_apply_patch` 定位来源
4. `steps_60` / `pane_60` 属调参，放最后
